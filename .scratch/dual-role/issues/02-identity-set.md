# 02: 身分解析改成回傳身分集合

**What to build:** 系統目前假設一個 LINE 使用者只有一個身分，查到教練就不再看學員。這張票拿掉那個假設：身分解析回傳這個人**擁有的所有身分**，由呼叫端決定要用哪一個。

完成後，具雙重身分的人可以手動在 LIFF 網址帶上頁面參數進到學員模式的畫面（例如請假頁）。切換入口還沒有，那是 03 的事——這張票要證明的是底層已經接得起來。

一般教練、一般學員、未註冊者的行為必須**完全不變**，這是這張票最重要的驗收條件。

同時把規格文件對齊現實：現行 SPEC 說雙重身分「以先註冊的角色為準」，但程式碼實作的是「教練永遠優先」，兩者從來沒有一致過。這張票之後兩者都作廢。

**Blocked by:** None (can start immediately)

**Status:** ready-for-human（實作完成，待真機驗收）

- [x] LIFF 開啟時的身分 API 同時回報這個人的教練身分與學員身分，而非二選一
- [ ] 雙重身分者手動帶頁面參數可以進到學員模式的畫面，且該畫面的 API 呼叫全部成功（授權層本來就支援，不該需要改動）
- [x] 沒帶頁面參數時，雙重身分者預設進教練模式
- [x] 一般教練、一般學員、未註冊者（含持邀請碼與不持邀請碼）的行為完全不變
- [x] SPEC 的角色章節改寫為支援雙重身分，並刪去「以先註冊的角色為準」
- [x] SPEC 的決策記錄表新增一列，指向 ADR-0001

## 實作紀錄

身分解析抽成 `lib/identity`：`resolveIdentities` 回傳身分集合，`primaryRole` 是**唯一**做
「二選一」的地方——雙重身分版 Rich Menu 上線時只有那個函式要改。`lib/line` 從此只管 LINE
平台這一側，不再碰資料庫。`?p=` 屬於哪一邊的判斷放在 `lib/liff-pages`，刻意與 `identity`
分開，因為它要被 client component 匯入，不能牽進 prisma。

已驗證：typecheck、lint、production build 全過；對真實資料驗過三種身分組合與九種 `?p=`
分流結果皆正確（含 `leaves`／`leave` 這組近似碰撞）。

**未驗證**：資料庫目前沒有任何雙重身分的資料（教練 YT 與學員 Jenny 是不同 LINE 帳號），
所以「雙重身分者手動帶參數進學員畫面」只驗到程式邏輯，沒有走過真機。需要一個同時存在於
兩張表的 LINE 帳號才能收掉最後一條驗收。
