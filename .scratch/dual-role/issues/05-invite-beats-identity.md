# 05: 已註冊的人也要能兌現邀請碼

**What to build:** 手上有一張還沒兌現、而且能給你一個你還沒有的身分的邀請碼時，就先讓你完成它——
不論你現在是不是已經註冊過。

目前 LIFF 入口只在「兩個身分都沒有」時才看邀請碼，已註冊的人一律直接看到自己的 App，
碼被靜默丟棄。註冊表單只有這一個入口，所以三條路同時被擋死：

1. 已是學員的人點教練邀請碼 → 看到學員畫面，無法成為教練
2. 已是教練的人點學員邀請碼 → 看到教練畫面，無法成為別的教練的學員
3. **已是學員的人被第二位教練邀請 → 邀請碼永遠用不掉，師生關係建不起來**

第 3 條與雙重身分無關，是既有缺陷，而且最嚴重：規格把「跨教練上課」列為連鎖健身房的常態，
學員註冊那支 API 也為此寫了整段合併邏輯（搬移課程、改指邀請、重建關係）——那段程式碼
目前從 LIFF 入口根本走不到，第二位教練會永遠看到那位學員是「未連結」。

判斷「這張碼能不能給你新東西」由伺服器做，前端只負責照著渲染。已註冊的人拿著一張失效的碼
不該被打擾，直接看自己的 App 就好；完全沒註冊過的人才需要看到「此邀請連結已失效」，
否則他會不知道發生什麼事。

**Blocked by:** None (can start immediately)

**Status:** ready-for-human（實作完成，待真機驗收）

- [ ] 已是學員的人點有效的教練邀請碼，看到教練註冊表單，完成後成為雙重身分
- [ ] 已是教練的人點有效的學員邀請碼，看到學員註冊表單，完成後成為雙重身分
- [ ] 已是學員的人點第二位教練的有效邀請碼，看到學員註冊表單，完成後兩段師生關係都在
- [ ] 已註冊的人點一張失效或不存在的碼，直接看到自己的 App，不被打擾
- [ ] 完全沒註冊過的人點失效的碼，仍看到「此邀請連結已失效」

## 實作紀錄

伺服器端新增 `describeInvite`：不論有沒有身分都查邀請碼，但只在「這張碼還能給他新東西」時
才回傳。回 null 就代表「不用理它，照常顯示他的 App」，兩種情況會這樣——已經是教練了還拿
教練碼，或碼失效而他已經註冊過。完全沒註冊過的人拿失效的碼仍會收到「已失效」，否則他會
不知道發生什麼事。

前端把邀請的優先序提到身分之上。原本順序相反，已註冊的人永遠走不到註冊表單，
而表單只有這一個入口。

順帶補上 `landOn`：註冊完成後停在他剛取得的那個身分。沒有這個，教練完成學員註冊後畫面
會跳回排課，跟當下綁上的 `member_dual` 選單對不起來——這是 03 那條「停在學員模式」的
驗收條件，直到這張票才真正到得了。

**注意**：教練註冊表單要求填「你的官方帳號」（`@abc1234` 或完整 line.me 網址），
`normalizeOaUrl` 不接受空值或其他格式。要成為教練的人得先有自己的 LINE 官方帳號。

**未驗證**：待真機走一次。

## 追加：註冊完成後回聊天室

原本註冊完成會重新拉 session、落在課表畫面。改成顯示成功畫面約一秒後 `liff.closeWindow()`，
把人送回聊天室——剛綁上的 Rich Menu 在那裡，而選單才是這套系統平常的入口，把人留在網頁裡
反而是死路。

停那一秒是因為註冊那兩支 API 都不發任何訊息。視窗直接消失的話，使用者回到聊天室只會看到
註冊前的舊畫面，唯一的變化是下方選單換了，很容易懷疑到底成功了沒。

`closeWindow` 只在 LINE 內有效，外部瀏覽器走 `onCannotClose` 退回原本的行為（顯示對應的
App，並停在他剛取得的那個身分）。`landOn` 因此保留，只是從常態變成退路。
