# 雙重身分以兩張表併存實作，模式狀態存在 LINE

MVP 原本明確不支援雙重身分（[SPEC.md](../../SPEC.md) §2），但「教練同時是另一位教練的學員」是真實存在的場景。
我們決定支援它，而且**不動資料模型**：`coaches` 與 `members` 的 `line_user_id` 唯一性本來就各自獨立，
同一個 LINE 帳號早就能同時存在於兩張表——`scripts/dev-role.ts` 就是靠這個特性運作的。
所有工程集中在「要給這個人看哪張臉」這一層。

## Considered Options

**抽出 `Person` / `User` 表，讓 Coach 與 Member 各自外鍵指過去。** 模型上正確得多，「一個人可以擔任多個角色」
會直接寫在 schema 裡。否決原因：需要 migration、兩張表的唯一約束要搬家、所有 `findUnique({ lineUserId })`
都要重寫，而此時已有正式資料。換來的好處在 MVP 階段是零——授權層 `requireCoach` / `requireMember`
本來就各自獨立查表，對雙重身分者現在就都會通。代價是「同一個人」這件事靠 `line_user_id` 欄位相等
隱性表達，沒有外鍵保護；此後每個碰到身分的人都必須知道這個約定。

**合併成單一畫面**（一張課表同時顯示「我要教的課」與「我要上的課」）。否決原因：兩邊的心智狀態
完全不同，混在一起之後每個畫面都要多一層「這是誰的課」的歧義，而排課、請假、設定這些寫入畫面
還是得分開，結果是半合併半分離、兩邊都不討好。改採兩套介面原樣保留、明確切換。

**iCal 訂閱合併輸出兩種課。** 這原本是補「切換身分導致看不到撞期」最便宜的地方，但被否決以維持
`icalToken` 掛在 `Coach` 上、iCal 語義等於「我要教的課」的單純性。撞期改由排課時的**警告（不阻擋）**
守住：排課 API 若發現該教練的 `line_user_id` 也在 `members`，就查他當 participant 的課有無時間重疊。
不阻擋是因為教練可能真的打算跟對方請假。

## Consequences

**「目前是教練模式還是學員模式」這個狀態存在 LINE，不存在資料庫。** 這是最違反直覺、最可能被後人
「修掉」的一點。切換走 LINE 原生的 `richmenuswitch`（客戶端瞬間切換），它會送 postback 給 webhook；
我們在收到時順手呼叫 `linkRichMenuIdToUser` 把綁定同步過去，於是 `getRichMenuIdOfUser` 就成為
「這個人現在在哪個模式」的權威答案。這讓我們在零 migration 的前提下，仍能正確回應純文字「課表」
這種需要知道當下模式的查詢。代價是每次切換多一次 LINE API 呼叫（免費，不佔推播額度），
以及模式查詢依賴外部服務可用性。

**Rich Menu 從 3 張變 5 張。** 新增 `coach_dual`（第二列改 4 格容納切換鍵）與 `member_dual`，
只綁給雙重身分者。刻意不改動一般教練的 6 格版——不讓 99% 的人為一個罕見功能付版面代價。

**教練端完全不顯示對方也是教練。** 延續 SPEC §4 的隱私硬規則：Y 眼中 X 就是一般學員。
這裡洩漏的會是「你的學員是你的同業」，比洩漏其他教練更敏感，而 X 從未同意過揭露此事。

**停用不收回選單。** X 被 Y 停用後 `members` 記錄仍在，仍視為雙重身分，學員模式點進去顯示空課表。
停用常常是暫時的，而教練端停用學員不該有副作用去動對方的 LINE 介面。
