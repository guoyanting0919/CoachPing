# 學員預約直接成立，不經教練核准

學員在教練宣告的**可預約時段**內按下預約，系統立刻建立一筆 `scheduled` 的課，教練事後收到推播。
不做「待審核」這一關——教練設定可預約時段本身就是事前同意，核准那一步拿不到任何新資訊來做判斷。
連帶決定：預約的產物就是既有的 `sessions` 記錄，**不新增 booking 表**，只加一個 `origin` 欄位記下它是誰發起的。

## Considered Options

**教練核准後才成立。** 直覺上是對的——那是教練的時間。否決的原因是它會逼出一個沒有好答案的問題：
待審期間那個時段要不要鎖住？鎖了，任何學員都能靠「送出預約再放置」把教練的整週佔到無法預約，
而系統沒有堂數包／扣抵機制（[SPEC.md](../../SPEC.md) §11）可以約束他；不鎖，則兩個學員同時送出後
必然有一人在等待數小時後被拒，而那幾小時裡他不會去約別的時間。兩條路都比「直接成立」差，
而直接成立的代價——教練偶爾得手動取消一堂不方便的課——是既有功能就處理得了的。

**比照請假的門檻自動核准**（提前夠久就自動成立，太臨時才轉申請，[SPEC.md](../../SPEC.md) §6）。
形式上對稱，但語義不對稱：請假的門檻在保護教練「已經排定的行程被臨時抽走」，
而預約根本還沒有行程可言。這裡對應的防線是 `bookingLeadHours`（最短提前時間）——
太臨時的時段直接不出現在學員的可選清單裡，而不是出現了再被拒。

**新增一張 `bookings` 表，核准後才產生 `session`。** 會讓「一堂課」存在兩種前身，
於此後每一段碰到課的程式碼（推播、請假、iCal、撞課偵測、教練課表）都要問一次
「這是 booking 還是 session」。`origin` 欄位用一個 enum 換到同樣的可追溯性。

## Consequences

**`Session.origin` 是落地欄位，不靠 `created_at` 反推。** 理由與 §15 對 `notifications.coach_id`
的論證相同：「這堂課是誰發起的」是發生當下才知道的事實，晚一天加欄位就永久少一天資料。
教練點開課表看到一堂自己沒印象排的課，第一反應是懷疑系統出錯——這個欄位是唯一能回答他的地方。

**取消完全複用請假流程，不需要寫任何「釋放時段」的邏輯。** 請假核准後 session 變 `cancelled`，
而可預約格子的計算只比對 `scheduled` 的課，時段因此自動回到可預約池。
副作用是學員取消自己約的課同樣受 `leaveDeadlineHours` 約束、臨時取消要教練核准——這是刻意的，
時段一旦被佔走，教練就已經把那段時間留給他了，「誰發起的」不改變「誰承擔損失」。

**沒有核准，濫用只能靠額度擋。** `Coach.maxOpenBookings`（預設 3）限制同一學員同時未上課的預約筆數。
這是系統裡唯一阻止學員把教練整週約滿的機制，動它之前請先讀懂上面否決「核准制」的理由——
把額度拿掉就等於把那個漏洞打開。

**預約的課沒有地點，而且我們刻意不補。** `sessions.location` 兩處畫面都會顯示，卻沒有任何輸入路徑
（[SPEC.md](../../SPEC.md) §4 明載排課表單不提供此欄位），所以現行每一堂課的 `location` 都是 null。
曾考慮加 `Coach.defaultLocation` 給預約的課帶入，否決原因是那會讓**只有學員自己約的課有地點**、
教練排的課永遠沒有——同一張課表上兩種課長得不一樣，比兩種都沒有更難解釋。
代價要說清楚：學員會收到一堂他從未與教練對話過的課、卻不知道要去哪，得自行到教練的 OA 詢問。
真要解，該解的是 `location` 的輸入路徑，不是在預約這條分支上補一個特例。
